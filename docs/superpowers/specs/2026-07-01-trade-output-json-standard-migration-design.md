# Design Spec: Trade Cockpit JSON Standard Migration

> **Status:** Draft — awaiting approval
> **Date:** 2026-07-01
> **Scope:** Migrate trade-ui role-output JSON from the 8-field wrapper to the
> 15-field `trade_output_v001` standard, including output-type renames and
> `simulation_id` lineage.

## 1. Purpose

The Trade Cockpit JSON Standard (`trade_output_v001`) was defined **after** the
V1.0 build and **after** the eToro demo integration spec. It mandates a stable
15-field top structure on every role-output JSON so the same file can drive
import, dashboard, journal, scoring, and learning uniformly.

This migration brings the live trade-ui codebase into compliance with that
standard. It is a **hard prerequisite** for V1.1 (eToro Demo Integration), which
links simulations via `simulation_id` — a field that does not yet exist in
produced output.

See downstream consumer:
`docs/superpowers/specs/2026-06-28-etoro-demo-integration-design.md` §1.1.

## 2. Current State — Three-Layer Drift

The standard exists in three inconsistent layers. Only the middle one is
enforced, which already breaks the daily pipeline.

| Layer | Top fields | `output_type` vocab | `simulation_id` | Status |
|-------|-----------|---------------------|-----------------|--------|
| **L1 — produced role output** (e.g. `031_*.json` from today's cron run) | 8 fields (missing 7) | `simulated_trade`, `score_result`, `learning_log_entry` | absent | **stale** — roles still follow old governance prompts |
| **L2 — code on disk** (schema + import, unstaged) | 15 fields **enforced** by `import_flow_output.py::validate_wrapper` | old names still in schema enum | null allowed | **mid-migration** |
| **L3 — the JSON standard** (this spec's target) | 15 fields | `simulation_order`, `simulation_score`, `learning_update` | required (TEXT `SIM-…`) | **not implemented** |

### Live breakage (must fix in this migration)

`import_flow_output.py` (L2) already rejects any file missing the 7 new fields
(`schema_version`, `flow_type`, `role_stage`, `input_refs`, `simulation_id`,
`evaluates_simulation_ids`, `quality`). Today's cronjob produced `031_*.json`
files (L1) that lack all seven → **`Run Import Now` rejects every 031 file.**
The daily pipeline currently produces unimportable output. This migration
restores a working end-to-end pipeline as a side effect.

## 3. The 15-Field Standard (target)

Every role-output JSON file MUST carry:

```json
{
  "schema_version": "trade_output_v001",
  "flow_run_id": "030",
  "flow_key": "trade_cockpit_simulation_v001",
  "flow_type": "daily_simulation",
  "role_key": "analyst01_trade",
  "role_stage": "analysis",
  "model_name": "minimax/MiniMax-M3",
  "created_at": "2026-06-29T16:45:00+02:00",
  "output_type": "candidate_analysis",
  "status": "completed",
  "input_refs": [],
  "simulation_id": null,
  "evaluates_simulation_ids": [],
  "quality": {
    "confidence": null,
    "data_quality": "unknown",
    "warnings": [],
    "missing_fields": []
  },
  "payload": {}
}
```

`payload` is role-specific and may evolve; the 15-field top structure is stable
across schema versions.

## 4. Role → stage → output_type (target vocabulary)

### Daily simulation flow (`flow_type: daily_simulation`)

| Role | `role_stage` | `output_type` |
|------|--------------|---------------|
| `trend01_trade` | `trend` | `trend_note` |
| `market01_trade` | `market` | `market_snapshot` |
| `analyst01_trade` | `analysis` | `candidate_analysis` |
| `risk01_trade` | `risk` | `risk_verdict` |
| `review01_trade` | `review` | `review_verdict` |
| `sim01_trade` | `simulation` | `simulation_order` ← renamed from `simulated_trade` |

### Periodic scoring/learning flow (`flow_type: periodic_learning`)

| Role | `role_stage` | `output_type` |
|------|--------------|---------------|
| `score01_trade` | `scoring` | `simulation_score` ← renamed from `score_result` |
| `learn01_trade` | `learning` | `learning_update` ← renamed from `learning_log_entry` |

> **Renamed output types (L3 vs L1/L2):**
> `simulated_trade → simulation_order`, `score_result → simulation_score`,
> `learning_log_entry → learning_update`. All other type names are unchanged.
> The `action` payload values (`SIMULATED_BUY`/`SIMULATED_SELL`) are **not**
> renamed — only the `output_type` label.

## 5. `simulation_id` Generation Convention

`simulation_id` is the canonical cross-flow link (simulation ↔ scoring ↔
learning ↔ eToro demo). Format:

```
SIM-{flow_run_id}-{SYMBOL}-{seq}
```

Example: `SIM-030-TSM-001`.

Rules:
- Generated by **sim01_trade** at emission time (the simulation step).
- `null` in early roles (`trend01`, `market01`, `analyst01` unless a candidate
  is already a trade setup, `risk01`, `review01`).
- `score01_trade` / `learn01_trade` do **not** generate ids; they populate
  `evaluates_simulation_ids` with the simulations they score/learn from.
- The Human/cronjob trigger does not generate ids.

## 6. Scope — What Changes

### 6.1 Schema (`schemas/role_output.schema.json`)
- `output_type` enum: rename the three types per §4 (clean cut — no dual vocab).
- Confirm all 15 fields are `required` (already true on disk).
- Add `role_stage` enum constraint matching §4.

### 6.2 Role governance prompts (`431–438_TRADE_*.md`)
- Instruct each role to emit the 15-field wrapper.
- Pin each role's `role_stage` and `output_type` per §4.
- sim01 (`436`): generate `simulation_id` per §5.
- score01/learn01 (`437`/`438`): populate `evaluates_simulation_ids`.
- All roles: populate `input_refs` with the upstream role outputs they built on
  (lineage), and `quality` where data confidence is knowable.

### 6.3 GATES (`docs/dpmtf/20_GATES.md`)
- §4.2 Final Output Types: replace the three renamed types.
- Add a `role_key → role_stage → output_type` permission table (mirrors §4).
- Add a `simulation_id` Required-Fields Gate for `simulation_order` outputs
  (sim01 may not emit `null`).
- Add an `input_refs` Lineage Gate (every non-first role must list ≥1 upstream
  ref in the same `flow_run_id`).

### 6.4 Database
- `simulated_trades`: add `simulation_id TEXT` (+ unique index).
- `score_results`: add `evaluates_simulation_ids TEXT` (JSON array) or a join
  table `score_simulation_links(simulation_id, score_result_id)`.
- Optional: `role_output_lineage` table to persist `input_refs` for queryable
  lineage (vs. only in `raw_json`).

### 6.5 Import (`scripts/import_flow_output.py`)
- `validate_wrapper` already enforces the 15 fields — keep.
- Update `output_type` allowed-set to the renamed vocabulary.
- Persist `simulation_id` into `simulated_trades` on import.
- Persist `input_refs` lineage (to the lineage table if added).
- Persist `quality` (either as columns or kept in `raw_json` + a
  `data_quality` denormalized column for the eToro Quality Gate query).

### 6.6 Frontend (`templates/index.html`, `static/js/app.js`)
- Daily panel: render `quality` badges (`data_quality`, `confidence`) on cards.
- Show `simulation_id` on simulation/score/learning cards.
- Bucket by `role_stage` where useful for grouping.

### 6.7 Tests (`scripts/test_v0*_gates.py`, `_v001_helper.py`)
- `_v001_helper.wrap()` already builds the 15-field wrapper — adopt it across
  all test scripts so staged fixtures validate.
- Add tests for the renamed `output_type` rejection (old name → rejected).
- Add a `simulation_id`-required test for `simulation_order`.
- Regression: 62/62 must still pass after the rename.

## 7. Out of Scope

- eToro demo integration (V1.1) — separate spec, downstream consumer.
- Renaming `action` payload values (`SIMULATED_BUY` etc.) — unchanged.
- Real trading / live account — never.
- Historical backfill of pre-standard runs — out of scope; old files in
  `inbox/processed/` keep their old format and are not re-imported.

## 8. Build Phases

### Phase M1 — Schema + vocabulary (0.5 dag)
- Rename `output_type` enum (§6.1).
- Update GATES §4.2 + permission table (§6.3).
- Add `role_stage` enum constraint.

### Phase M2 — Role governance prompts (1 dag)
- Update `431–438_TRADE_*.md` to emit 15-field wrapper with pinned
  `role_stage`/`output_type`.
- sim01 `simulation_id` generation (§5).
- score01/learn01 `evaluates_simulation_ids`.

### Phase M3 — Database schema (0.5 dag)
- `simulation_id` on `simulated_trades` (+ index).
- `evaluates_simulation_ids` / link table on `score_results`.
- Optional `role_output_lineage` table.
- Idempotent migration in `scripts/init_db.py`.

### Phase M4 — Import + persistence (1 dag)
- Rename-allowed-set in import (§6.5).
- Persist `simulation_id`, `input_refs`, `quality`.
- Restore end-to-end import of a fresh cron run (fixes the 031 breakage).

### Phase M5 — Frontend (1 dag)
- `quality` badges + `simulation_id` display (§6.6).

### Phase M6 — Tests + regression (0.5 dag)
- Adopt `_v001_helper.wrap()` in all test scripts.
- Add rename-rejection + `simulation_id`-required + lineage tests.
- 62/62 regression (under new vocabulary).

## 9. Validation

- `python3 -m py_compile app.py scripts/import_flow_output.py scripts/init_db.py`
- `node --check static/js/app.js`
- `python3 scripts/init_db.py` (idempotent migration).
- Full cron run: `bash scripts/trade-cronjob.sh` → all 6 outputs import cleanly
  via `Run Import Now` (no rejections), `simulation_id` populated on the sim01
  row.
- 62/62 gate tests pass under the renamed vocabulary.
- Manual: Daily panel shows `quality` badges and `simulation_id`.

## 10. Sequencing

```
JSON-standard migration (this spec)  ──▶  V1.1 eToro Demo (Fase 2+)
   • restores importable daily output
   • introduces simulation_id
   • renames output types
```

V1.1 eToro Fase 1 (Bridge Core) may overlap with M5–M6. V1.1 Fase 2 (Trade
Execution) is blocked until this migration lands.
